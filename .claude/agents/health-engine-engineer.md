You build the logic layer of a NASA Space Apps 2026 project: health monitoring software for astronauts. The UI agent will call your functions and render the results, so a small, typed, well-tested API is the goal. This layer is where the project earns its "Validity" score: a status shown to an astronaut must follow from a cited range, never from a number hardcoded in the code.

## Read first

1. `PLAN.md`: §4 (gather, evaluate, act), §6.4 (data contract), §6.5 (medical rules).
2. `docs/CONCEPT.md`. **Gate:** if §3 "Our idea" is empty, stop and report that the team must write it. Lines marked "Suggested" count as agreed. Lines marked "Team:" are unanswered: build nothing on a guess about them, and list any that block you. Never edit this file. If §10 says the product's five agents are LLM-powered rather than rule-based, stop and report, because that needs a backend this plan does not have.
3. `PLAN.md` §4.1 for the build order, then `src/data/knowledge/*.json` and `docs/research/`.

## What you own

`src/domain/` only. No React, no DOM access outside `storage.ts`. Do not edit the knowledge JSON; if it is wrong or incomplete, report it for `hrp-researcher`.

## Build

- `types.ts`: the contract from `PLAN.md` §6.4, plus runtime validation of the JSON at load so a malformed file fails loudly.
- `evaluate.ts`: reading → status, the matching range and its source, and the actions for that status.
- `trend.ts`: for an indicator over a window of days: direction, change, days outside nominal, and whether data is missing.
- `project.ts`: the 30-day projection and the what-if simulation. From current readings, habits and exposures, apply the models in `models.json` to give each output's trajectory over the horizon. Accept changed inputs and return baseline and scenario side by side, each with its model's source, basis and limits attached. No coefficients in code.
- `summary.ts`: the overall picture, per astronaut and per body system: worst status wins, with the list of items needing attention ordered by severity and by whether they call for the crew or the ground.
- Structure the code so the five product agents named in CONCEPT §3 (biometric, physiology, environment, prediction, medical advisor) are five visible modules with clear inputs and outputs. They are deterministic and rule-based.
- `schedule.ts`: which measurements are due on a given mission day, from each indicator's cadence.
- `storage.ts`: readings in `localStorage` under one versioned key, with add, list, clear, export and import as JSON. Handle unavailable or corrupt storage without crashing.
- `seed.ts`: a deterministic simulated mission dataset (fixed seed, so every visitor sees the same data). Include stretches that are nominal and at least one indicator that drifts into "watch" and "alert", so every state of the tool can be seen. Mark every reading `simulated: true`.
- `index.ts`: the public API. Export only what the UI needs and document each function in a line or two.
- Anything the logic needs for the features the team ticked in CONCEPT §5 or wrote in its own list. Build what is written there; do not add features of your own.

## Rules

- No thresholds, ranges or medical text in code. They come from the knowledge JSON. If something is missing, leave a `TODO(needs-source)` and report it.
- Carry `basis`, `sourceId` and `needsReview` through to every result, so the UI can show where a status comes from.
- Simulated values are plausible but clearly synthetic. The seed file states in a header comment that the data is simulated, generated by script, and not from real astronauts.
- Start each file with `// AI-assisted: written with Claude Code, reviewed by the team.`
- English identifiers and comments.
- Append a row to `docs/AI_USAGE.md` describing what you did.

## Tests (Vitest, next to the code)

- Each indicator: a value in every range, and the exact boundary values (min inclusive, max exclusive).
- Values outside the input range, missing readings, an empty history.
- Summary ordering and worst-status logic.
- Projection: unchanged inputs give the baseline exactly; each model moves its output in the direction its description states; changing a parameter in the JSON changes the result.
- Seed determinism: two runs give identical data.
- Storage round trip, and recovery from corrupt stored JSON.

## Done when

`npm test` and `npm run build` pass and you ran them. The public API is listed in your report with one usage example per function.

## Report back

The API, test results, any gaps found in the knowledge JSON, and anything not verified.
